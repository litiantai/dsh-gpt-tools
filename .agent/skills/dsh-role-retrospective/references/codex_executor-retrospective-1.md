用中文复盘结构化输入中的全部研发证据，按 daily_retrospective schema 输出报告内容和需求候选；HTML 由控制器确定性生成。模型不修改文件、不写台账、不调用生产服务。

status 表示本次复盘执行是否完成：问题已如实分析、候选有证据时输出 pass，即使项目存在缺陷或卡点也不改变这一执行结论；分析自身失败、缺少必需证据或无法完成才使用 fail/blocked。项目健康、历史问题和当前卡点在对应事实字段说明，不能将 pass 解读成项目无问题。

逐类核对任务与返修、巡检步骤与信号、独立验证、方案/验收审查、代码评审与交付、需求池和队列。coverage 记录实际读取的来源、记录 ID、完整性及缺口；输入缺少、截断或不可读取时明确说明，不能用没有 blocked 任务替代全面复盘，也不能推断“无问题”。只有全部适用来源完整覆盖且没有问题证据时才写“无”。旧回执缺少新字段时同样注明覆盖未知。

按北京时间区分输入的统计窗口与当前快照。完成、发生、恢复和反复出现的时间以真实记录为准；没有状态历史就标记历史不完整。区分已验收、已合入、已发布、观察中与正式复验；observed、截图采集成功、健康检查、模型声明和候选测试通过，均不能替代业务断言 pass 或正式上线后的效果。

problem_items 保留完整问题、来源 ID、失败类型、实际证据、signal_ids、已有 requirement_ids、窗口状态、当前状态与下一步。当前等待使用结构化进度判定：额度、低峰、资源槽、依赖、项目暂停、人工控制、环境缺失或模型执行故障与代码/业务缺陷分开。旧失败不能冒充当前仍阻塞；恢复必须有对应场景、版本与断言证据。

能转化的真实缺陷或优化写入 requirement_candidates，每项关联实际输入的 signal_ids，提供 evidence、impact、reproduction、acceptance、classification、in_scope、priority 和 existing_requirement_id。不得编造信号或需求 ID。与已有需求同因时引用 existing_requirement_id，保留本轮新增证据；已修复未上线仍关联原需求。原任务范围内的返修继续原任务，不因多次失败重复造需求；已完成后出现新的回归需保留新版本证据，不把历史完成误认成当前已解决。

development 必须有针对原问题、经源码核对的可执行 resolution_probes 与验收条件，不能用泛化健康检查凑数。缺证据或原因未明用 investigation；凭据、网络、工具、运行实例等障碍用 environment；正常额度/时段/执行槽等待只报告等待与恢复条件。只有证据证明等待机制本身存在缺陷或存在可验收优化，才另提流程/代码改进。范围外问题明确说明，不自动派发。

用户已授权需求转化时，控制器核对来源、版本、已有需求和去重后使用现有入池 API；模型输出候选不代表入池成功。报告最终以控制器返回的真实新增、复用、调查、待确认、未入池状态和关联任务进展为准，不绕过原开发、独立验证、审查或发布门槛。详细字段与产物见 [report-contract.md](report-contract.md)。

完整证据较大时，输入提供 retrospective-evidence 目录、manifest.json 与分页索引。先核对 manifest 的全部类别与数量，逐页读取全部索引；标有 excerpt 或涉及需求转化的对象必须读取 detail_file 原文。索引省略的是重复回执正文，不是任务或问题；无法读取的页和对象必须记入 coverage 缺口，不能宣称已完成全面归因。只读取本次执行目录中的脱敏证据，不访问原台账或凭据。
